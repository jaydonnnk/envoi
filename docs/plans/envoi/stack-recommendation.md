## Recommendation

Use a **TypeScript application with Next.js, a Node backend/worker, Supabase PostgreSQL/Auth and Render hosting**. Keep one deterministic payment-rule implementation shared by the buyer app, merchant view, API and MCP. Include **APIMatic** for PayPal context and account-supported API tooling, and **Zapier** for a separate menu-image draft workflow. Start with PayPal sandbox; add wallet-signed devnet PYUSD after independent proof. All choices remain provisional; no application or sponsor integration exists.

## Hosting including production

**Hackathon:** proposed Render Node web service in Singapore plus a Render worker for reconciliation and import cleanup; Supabase database/auth in Singapore. The web service receives external results; workers have no inbound HTTP endpoint. Next.js supports Node deployments and Render documents this deployment path. No service or sponsor credits have been provisioned. [Next.js](https://nextjs.org/docs/app/getting-started/deploying), [Render deployment](https://render.com/docs/deploy-nextjs-app), [Render regions](https://render.com/docs/regions), [service types](https://render.com/docs/service-types).

**Production pilot:** paid always-on Render web/worker services, paid Supabase with a recovery configuration suited to the agreed data-loss tolerance, separate environments, managed secrets, a paid Solana RPC only if the live wallet rail is approved, and a custom HTTPS domain. Select backup/PITR and compute sizes after defining recovery targets and load. Do not claim free tiers, regional co-location, or sandbox reliability satisfy production needs. No services have been provisioned and no budget is assumed.

Keep payment jobs outside a page request; persist status before responding. A webhook, callback or RPC observation is input to verification, not automatic authority to set "paid". Use a server-verified captured order or finalized, semantically verified token transfer as the success boundary. Separate payment status from merchant acknowledgment.

## Proposed menu workflow boundary

Merchant's separate menu image -> consented temporary storage/access -> AI by Zapier draft -> Node validation -> merchant correction, availability and explicit confirmation -> authorized publication. This is an architectural candidate for Gate 2, not an approved contract.

Supabase private Storage with short-lived direct signed URLs is a candidate for image delivery. Prove Zapier/provider fetch compatibility and early source removal before choosing it: Auth key revocation does not invalidate those URLs. If deletion/cache behavior cannot meet the removal requirement, choose a revocable serving approach at Gate 2. Do not use Render's ephemeral filesystem as the only durable upload/job store. Remove source access after completion/failure/cancellation/expiry, with worker cleanup after crashes; set the precise windows at Gate 2. Envoi cleanup cannot promise deletion from third-party history or caches. [Supabase serving](https://supabase.com/docs/guides/storage/serving/downloads), [Render filesystem](https://render.com/docs/faq).

Keep import results scoped to an authenticated merchant/outlet and current draft. Reject malformed/empty output, leave unknown prices blank, preserve merchant edits and ignore duplicate/late results. No Zap write path may publish a menu or execute payments. Menu edits invalidate confirmation; payment-relevant changes require fresh buyer approval. Authentication/transport, limits, timeout/retry contracts and deletion evidence belong to later gates.

Zapier needs account access and task budget through judging; the published workflow cannot depend on a 14-day trial remaining active. APIMatic own-API clients/documentation remain conditional on the actual tier. The proposed sponsor trio does not establish prize eligibility. See `research.md` for checked primary documentation and unresolved access.

## Why this over the alternatives

- Next.js + Fastify from day one is reasonable if the MCP server needs framework middleware, but it adds another server boundary before a purchase works. Prefer one app first; decide on a separate API with concrete transport evidence at Gate 2.
- FastAPI + Python adds a second language across browser wallets, PayPal tooling and public clients. Use it only if an existing team capability makes that trade worthwhile; none is established here.
- OpenAI Agents SDK is a viable alternative to Vercel AI SDK. Pick one orchestration layer, not both. This product needs constrained tools and deterministic rules, not a multi-agent framework to calculate payment amounts.
- Vercel hosting is a viable frontend alternative, but the durable worker would still need a host. Render keeps the initial web/worker deployment together and is a listed sponsor. Sponsor prize eligibility is checked separately in `research.md`.

## Production decisions technology cannot settle

1. **Provider eligibility:** prove the platform can receive live partner approval and Singapore sellers can use the chosen onboarding path. Sandbox access is not a promise of live approval.
2. **Regulatory treatment:** no custody alone does not determine exemption. Obtain qualified review of the actual service, including token-transfer facilitation. [MAS expanded scope](https://www.mas.gov.sg/regulation/notifications/expanded-scope-of-the-payment-services-act-2019).
3. **Merchant economics:** validate whether the merchant accepts the fee schedule, USD asset exposure, off-ramping burden and support/refund obligations. A cheap network fee is not a cheap complete purchase.
4. **Buyer approval:** a review button starts PayPal or wallet approval; it cannot silently manufacture buyer consent.
5. **Launch evidence:** actual recipient verification, duplicate handling, uncertain-result recovery, restore drill and named support ownership must pass before a live pilot.

These are launch blockers, not reasons to stop a sandbox hackathon plan. Keep mainnet and live credentials disabled until the relevant production gates are approved.
