## Recommendation

**[hypothesis]** Use **Next.js/TypeScript on Render Free, Neon Free PostgreSQL, Better Auth inside the app and finite hourly GitHub Actions maintenance**. Supabase and the paid Render worker are superseded. Store bounded temporary menu images as private database bytes served through the revocable Envoi proxy. Keep shared deterministic purchase rules, a direct PayPal Orders v2 sandbox adapter with a distinct authorized seller, APIMatic development tooling and Zapier draft-only menu import. PYUSD remains disabled pending proof and a Gate 2 amendment. These are approved proposal choices; account access, quotas and integration performance remain unknown.

## Hosting including production

**[hypothesis] Hackathon:** one Render Free Node web service, Neon Free database and an hourly finite GitHub Actions maintenance job. Choose available nearby regions after account verification; Singapore co-location is unverified. No services/credits have been provisioned and no billable fallback is allowed. The app receives provider results and performs buyer-requested payment calls; durable recovery remains in the database.

**[vendor claim] Limits:** Render Free sleeps after 15 minutes idle, may take about a minute to wake, has shared monthly instance hours and an ephemeral filesystem. Render Free Postgres expires after 30 days; there is no free Render worker/disk. Neon documents 1 GB/project Postgres storage, 100 CU-hours/project/month and 5 GB transfer/project/month, with five-minute scale-to-zero. Its quota-limited Free plan describes no 30-day expiry; account access/usage are still unverified. Capacity exhaustion can suspend reads or block cleanup writes. [Render Free](https://render.com/docs/free), [Neon plans](https://neon.com/docs/introduction/plans).

**[unknown] Scheduled execution:** standard public GitHub runners are free; a private repository consumes included minutes shared with other jobs. Verify remaining quota and a zero-spend stop setting. The separate Git request permits planning commits only; no repository visibility change, maintenance workflow or deployment is authorized. Schedules can be delayed/dropped; proposed hourly cadence/two-minute run timeout must be measured with build/CI usage and Neon wake time. No image/payment artifacts or caches in maintenance. These are access proofs before release, not installed workflows.

**Production pilot:** outside the current request. Define availability, recovery, storage/retention, mail/support and capacity needs before proposing a paid budget or revised topology. Free tiers/sandbox behavior do not establish production readiness.

Persist an attempt and due state before each payment request. No fire-and-forget work after an HTTP response. Webhooks/callbacks trigger verification, not automatic paid status. Only a server-verified capture or finalized semantically verified transfer can confirm payment; acknowledgment stays separate.

## Menu workflow boundary selected in the approved Gate 2 proposal

Merchant's separate menu image -> consented bounded private database bytes + Envoi image proxy -> web request dispatch -> AI by Zapier draft -> authenticated result + Node validation -> merchant correction, availability and explicit confirmation -> authorized publication. This is an approved proposal with unresolved review findings and an untested contract.

Use a proxy checking capability/state/deadline on every fetch and returning bytes without redirect/caching. Proposed fetch/result window: five minutes. Completion/failure/cancel transactionally deletes the source row; expiry denies access even if no job runs. Idle/crash source removal is best effort hourly, with no five-minute deletion or hard physical-retention guarantee. A proposed 90-minute stale-maintenance/overdue-source threshold blocks new imports and requires operator cleanup. Database restore history/upstream copies can outlive logical deletion; consent must explain this. This supersedes the earlier Storage/five-minute deletion draft.

Proposed input: one JPEG/PNG at most 5 MiB before/after normalization, 20 megapixels/6,000 pixels per side; ten sources/50 MiB live bytes across the demo. Monitor total database/history usage with headroom; these caps do not bound provider storage. Limits and fetch/denial/removal remain untested; real-image imports stay blocked until proof and informed consent. Local browser preview does not extend server retention. See `02-architecture.md` for complete controls. [PostgreSQL binary data](https://www.postgresql.org/docs/current/datatype-binary.html).

Keep results scoped by a per-import bearer token and original draft revision. Proposed bounds: 100 rows, 120 characters per name/portion and 128 KiB per callback. Reject malformed/empty output, leave unknown prices blank, preserve edits and ignore duplicate/late results. No Zap write path publishes or executes payments. Menu edits invalidate confirmation; affected purchases need fresh buyer approval. No automatic re-analysis; retries need fresh merchant consent/access. Exact types/races/tests belong to Gate 3; runtime deletion evidence belongs to authorized slices.

Free hosting does not establish free AI/Zapier access. Zapier needs a supported published workflow/model and task access through judging; a short trial is insufficient. APIMatic own-API clients/docs remain account-conditional. Sponsor prizes and credits remain unverified. See `research.md`.

## Why this over the alternatives

- Next.js + Fastify adds another server boundary before a purchase works. The approved Gate 2 proposal selects one app first; a demonstrated MCP transport constraint would justify revising that decision.
- FastAPI + Python adds a second language across browser wallets, PayPal tooling and public clients. Use it only if an existing team capability makes that trade worthwhile; none is established here.
- OpenAI Agents SDK is an alternative; the approved Gate 2 proposal selects Vercel AI SDK only. This product needs constrained suggestions and deterministic rules, not multiple orchestration layers to calculate payment amounts.
- Render can host both app and database, but its free database expiry and paid-worker requirement fail the current constraint. Neon Free supplies persistent database capacity while the app stays on Render; free access and recovery still need proof. Supabase is unnecessary and currently unavailable to the user. Alternate hosting would require a Gate 2 revision.

## Production decisions technology cannot settle

1. **Provider eligibility:** prove the platform can receive live partner approval and Singapore sellers can use the chosen onboarding path. Sandbox access is not a promise of live approval.
2. **Regulatory treatment:** no custody alone does not determine exemption. Obtain qualified review of the actual service, including token-transfer facilitation. [MAS expanded scope](https://www.mas.gov.sg/regulation/notifications/expanded-scope-of-the-payment-services-act-2019).
3. **Merchant economics:** validate whether the merchant accepts the fee schedule, USD asset exposure, off-ramping burden and support/refund obligations. A cheap network fee is not a cheap complete purchase.
4. **Buyer approval:** a review button starts PayPal or wallet approval; it cannot silently manufacture buyer consent.
5. **Launch evidence:** actual recipient verification, duplicate handling, uncertain-result recovery, restore drill and named support ownership must pass before a live pilot.

These are launch blockers, not reasons to stop a sandbox hackathon plan. Keep mainnet and live credentials disabled until the relevant production gates are approved.
